# CQ-020 — Post-development notes

Both units are complete: unit 1 (backend) and unit 2 (LO console frontend), on the same branch.

## Summary

`POST /packages/{id}/send` checks readiness (409 plus the blocker list when not ready) and starts the Temporal `SendQuotePackageWorkflow`. The workflow runs four idempotent activities. **Freeze** writes a `quote_package_versions` row with the token, `sent_at` and `expires_at` (+21 days). **Render** makes the WeasyPrint PDF and stores it in MinIO at a per-version key. **Email** sends a table-based HTML + text email with the PDF attached through SMTP/Mailpit, and always writes an `outbox_emails` row. **Record** sets status Sent and writes one activity event and one CRM event. The Send tab polls progress with `GET /send-status` and lists history with `GET /versions`; `GET /letter.pdf` streams a stored PDF. A PUT on a sent package reopens it as the draft (M3), and a PUT while a send is in flight is a 409. Two PR #22 minors are fixed or logged.

**Unit 2 (LO console).** The Send tab's confirm dialog now sends: `POST /send`, then a step list (Rendering letter → Emailing → Done) polled every 500 ms from `GET /send-status`. A 409 `PACKAGE_NOT_READY` lists the blockers in the dialog, and a failed send shows its error with "Try again". On done, a "Sent to {email}" toast appears, the header pill turns Sent (workspace summary refetch) and a "Sent versions" list shows each version: timestamp, Current/Superseded, "Download PDF" (`letter.pdf?version=N`) and "Open in Outbox" (`/outbox?email={id}`, CQ-029's route, plan.md Decision 17). Editing is locked while a send runs. A PUT refused with 409 `SEND_IN_PROGRESS` reverts to the server's package and follows the running send. The third PR #22 minor, where a failed save could be silently dropped by a later successful save, is fixed: failed edits ride along with every later save until one succeeds, and a Retry button re-sends them (Decision 20). Files: `apps/lo-console/src/features/send/` (`useSendFlow.ts`, `SendProgress.tsx`, `SentVersions.tsx`, `SendToast.tsx`, `versions.ts`, plus changes to `api.ts`, `useSendTab.ts`, `SendButton.tsx` and `SendTab.tsx`), `apps/lo-console/src/lib/api-client.ts` (`API_BASE_URL`), `e2e/p3-milestone-send-to-report.spec.ts` (P3 milestone and LO send-flow tests, one serial file), `e2e/p3-milestone-send-to-report.spec.ts`, `e2e/helpers/{send,mailpit}.ts`, `playwright.config.ts` (cross-app project). A backend fix came out of the full e2e run (Decision 21).

### Review findings (PR #30, re-review round)

| Severity | Finding | Resolution |
| --- | --- | --- |
| Minor | (1) `start_send`'s `except` branch, on a `start_workflow` failure, recorded the *new* `workflow_id` as `failed` even when Temporal had actually accepted and started that run (a client-side RPC error, e.g. a deadline, after the server-side start succeeds). The orphan run then kept executing under an id the package no longer tracked as "failed", and Freeze's `SendSupersededError` guard (Decision 22) compares `package.send_workflow_id` to the run's own id -- pointing the package *at* the orphan made that comparison match, so the guard couldn't stop it: the orphan would freeze and email normally, and a retry started a second, genuinely double send | Fixed: the `except` branch now leaves `send_workflow_id` at whatever it was before the attempt (never this attempt's id) and records only the failed status/error. Freeze then sees the orphan's id doesn't match and raises `SendSupersededError`, so the orphan freezes and emails nothing. Test (RED before the fix): `test_start_send_orphan_is_superseded_not_double_sent` -- starts a real run via a client that raises after Temporal accepts it, asserts `send_workflow_id` is untouched, the orphan's own run returns `""` with no version/email, and a retry sends exactly once |
| Minor | (2) `reconcile_send` called the lazy `await temporal()` provider *outside* `_send_is_alive`'s `try`, so on a fresh process with Temporal unreachable, the provider's own connection failure raised straight through `reconcile_send` into `GET /send-status` and `PUT /package` (500), instead of the documented "Temporal unreachable = benefit of the doubt (still in flight)" behaviour | Fixed: `_send_is_alive` now takes the `TemporalProvider` itself and awaits it inside its own `try`/`except`, so a provider failure is caught the same way a reachable-but-erroring Temporal call already was. Test (RED before the fix): `test_reconcile_survives_an_unreachable_temporal_provider` -- overrides `get_temporal_client` with a coroutine that raises `ConnectionError`, asserts `GET /send-status` still returns 200 (`rendering`) and `PUT /package` still returns 409 `SEND_IN_PROGRESS` instead of 500 |
| Minor | (3) `SEND_EXECUTION_TIMEOUT` (10 min) was shorter than the send activities' worst-case retry budget: at the old shared `ACTIVITY_TIMEOUT` (60s) and `SEND_RETRY_POLICY`'s 5 attempts, one activity's worst case was 5×60 + (1+2+4+8) = 315s, and all four (freeze/render/email/record) together could reach ~1260s (21 min) -- more than double the execution timeout. A persistently failing SMTP/MinIO step could then be cut off by Temporal's execution timeout *before* the workflow's `except` block ever ran `mark_send_failed`, leaving the package stuck "in flight" (relying only on `reconcile_send`'s later poll to notice) | Fixed: a new, tighter `SEND_ACTIVITY_TIMEOUT` (20s, `app/workflows/retry_policies.py`) for freeze/render/email/record brings the same worst case down to 4×(5×20+15) = 460s (~7.7 min), comfortably under the 10-minute execution timeout. `mark_send_failed` keeps the shared 60s `ACTIVITY_TIMEOUT` (it's the cleanup step, not part of this budget). Test (RED before the fix -- fails on import since `SEND_ACTIVITY_TIMEOUT` didn't exist yet): `test_send_execution_timeout_exceeds_the_worst_case_retry_budget` (`backend/app/workflows/tests/test_retry_policy.py`) computes the worst-case budget from the live `SEND_RETRY_POLICY`/`SEND_ACTIVITY_TIMEOUT` and the actual number of `SEND_RETRY_POLICY` activities in `SendQuotePackageWorkflow.run`, and asserts `SEND_EXECUTION_TIMEOUT` exceeds it |
| Minor | (4) `start_workflow` (in `start_send`) and the `describe` call the double-click check and `reconcile_send` share (via `_workflow_running`) both run while the caller holds the package row lock, with no `rpc_timeout`, so a slow/hung Temporal could hold that lock open indefinitely | Fixed: both calls now pass `rpc_timeout=TEMPORAL_RPC_TIMEOUT` (5s, `app/features/quotes/delivery/service.py`). Test: `test_start_send_and_workflow_running_pass_an_rpc_timeout` spies on both calls' kwargs |

- No backend Dockerfile exists; CQ-035 must install Pango (`libpango-1.0-0 libpangoft2-1.0-0`) in the Railway image.
